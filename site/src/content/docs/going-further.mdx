## Build logs and detach

`run`, `rebuild` and `start` print their build and also write it to the instance's build log. Closing the terminal doesn't stop a build; Ctrl-C cancels it (a cancelled `run` is undone). `-d` returns as soon as the instance is registered:

```bash
devsandbox rebuild -d --force web       # prints: web, the build goes on
devsandbox logs --build web --follow    # until it's up or failed
devsandbox logs web                     # the container's own log
```

A failing `postCreateCommand` aborts `run` but keeps the container, so `logs` and `exec` can show you why.

`--service` opens a terminal in a service container the instance uses:

```bash
devsandbox exec web --service database -- psql -U postgres
```

## Get a shell back

```bash
devsandbox exec web --sessions                # id, state, attached or detached, started, command
devsandbox exec web --attach                  # the detached session, else the running one; a pick list if several
devsandbox exec web --attach=1790000000-a1b2  # a given one
devsandbox exec web --session 1790000000-a1b2 pnpm dev  # run in that session, or attach if it's live
devsandbox exec web --end 1790000000-a1b2     # end a session (its program gets SIGHUP)
```

An `exec` from a terminal runs in a session that survives a closed terminal or a dropped connection, dashboard terminals included; sessions end with their program, `--end`, or the container.

## Who you are inside

Inside a sandbox you are the config's `remoteUser` (else `containerUser`, else the image's `USER`) with your host uid/gid, on every runtime, so workspace files stay yours. `run` says how in one `identity:` line; `--reprobe` probes the runtime again after you change its setup.

Mount into that user's home with `${containerEnv:HOME}` ([variables](/docs/config#variables)):

```toml
mounts = ["source=${localEnv:HOME}/.claude,target=${containerEnv:HOME}/.claude,type=bind"]
```

To take the image's users as written, nothing remapped, set [`identity = "image"`](/docs/config#devsandbox-extras) on the sandbox.

### Configs written for root

A config that mounts into `/root` or sets a root user gets a prompt before `run`, `start` and `rebuild`:

```text
[u]pdate / [c]ontinue as is (don't ask again) / [s]kip this time
```

`u` rewrites `devsandboxes.toml` (`/root` → `${containerEnv:HOME}`, root user removed, comments kept) and names the instances to `rebuild`; `c` keeps it as `identity = "image"`; `s` goes ahead this once.

## Links open on your desktop

`xdg-open`, `$BROWSER` and a CLI's "press enter to open the browser" in a sandbox open the link in your host's browser. Only `http(s)` URLs open. A `localhost` URL or an OAuth callback (`gh auth login`) gets a port forward first, so it reaches the container. From a script, `devsbd open <url>`. Existing instances get it once rebuilt.

[Profiles](/docs/config#profiles-profilesname) pick which browser:

```toml title="devsandboxes.toml"
[profiles.work]
[profiles.personal]

[sandbox.web]
folder = "../web"
image = "node:22"
profiles = ["work", "personal"]   # the ones its instances may be in
```

```toml title="~/.local/share/devsandbox/profiles.toml"
[work]
open = ["google-chrome", "--profile-directory=Profile 2"]
```

```bash
devsandbox run web --profile personal   # default: the last one picked, else the first
devsandbox profile web work             # switch, nothing restarts
```

`P` in the dashboard does the same. A profile `profiles.toml` doesn't map opens with the system opener.

## GPUs

`hostRequirements.gpu = true` on a sandbox or a service gives its container every NVIDIA GPU; `"optional"` runs without one when none is usable. A required GPU that isn't usable stops `run` before anything is built, saying why. [Details](/docs/config#implemented-devcontainer-properties).

```toml
[sandbox.ml]
folder = "../ml"
image = "pytorch/pytorch"
hostRequirements.gpu = true
```

## The host daemon

`run`, `rebuild`, `start`, `stop`, `rm`, the dashboard, port forwards, notifications and links all go through `devsandbox serve`, one per user. It starts on demand and exits after 10 minutes with nothing to do; files (`state.toml`, the Inbox) stay the source of truth, so stopping it loses nothing. Builds run with your shell's environment and keep going without the terminal. Linux and macOS.

A sandbox the runtime restarts on boot (`autostart = "runtime"`) needs it running from login:

```bash
devsandbox serve install     # a systemd user unit (Linux) or a LaunchAgent (macOS); never idles out
devsandbox serve uninstall
```

To only keep it from idling, without a unit:

```toml title="~/.local/share/devsandbox/daemon.config.toml"
[serve]
keep-alive = true
```

Anyone who can open its socket can act as you on every sandbox, like `docker.sock`. Editors and GUIs talk to it over a JSON-lines API: `devsandbox api --stdio`, or the [Node API](/docs/node-api)'s `connect()`.
