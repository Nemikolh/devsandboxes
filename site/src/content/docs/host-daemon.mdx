`devsandbox serve` is a small background process, one per user, that holds the live side of devsandbox on your machine: the `run`, `rebuild`, `start`, `stop`, `rm` and `service rebuild` you start, everything the dashboard shows, the connection to each running sandbox's helper, the ssh-agent relay, port forwards, desktop notifications, the control commands dispatchers use, and the API other tools talk to. Because it lives outside the dashboard and your terminal, all of that keeps working when you close them.

## You don't start it

The dashboard, `run`, `rebuild`, `start`, `stop`, `rm`, `service rebuild` and the commands that relay your ssh-agent start it when it isn't running, and a newer devsandbox takes over from an older one by itself. It exits 10 minutes after its last user left: no dashboard, no build or other command still running, no port forward, no running dispatcher or `inbox = true` sandbox. Files stay the source of truth (`state.toml`, the Inbox), so stopping it loses nothing, and read-only commands such as `ps` or `devsandbox inbox ls` don't need it.

What it keeps across restarts:

- **Builds.** A `run`, `rebuild` or `start` keeps going when the daemon hands over to a newer one, and the next daemon picks it up. It runs with the environment of the shell that started it, not the daemon's, so `${localEnv:…}` and your ssh-agent are yours. With no daemon reachable, the command warns and runs in your terminal instead.
- **Port forwards.** Ports-tab forwards survive closing the dashboard and come back on the same host port when the daemon restarts; a sandbox's `forwardPorts` follow its instance.
- **Dispatchers.** `devsbd ensure`, `exec`, `events` and the rest are served whether or not a dashboard is open. A control command exits `75` only when no daemon is reachable; scripts retry.

## Start it at login

A sandbox the container runtime restarts on boot (`autostart = "runtime"`) can't start a host process itself, so until your first `devsandbox` command its control commands wait. Hand the daemon to your service manager to close that gap:

```bash
devsandbox serve install     # a systemd user unit (Linux) or a LaunchAgent (macOS)
devsandbox serve uninstall
```

The installed daemon never idles out and follows upgrades: a newer devsandbox repoints the unit at its own binary. Run `install` again after changing `PATH` or your container runtime's settings. To only keep the daemon from idling, without a unit, set it in `~/.local/share/devsandbox/daemon.config.toml`:

```toml
[serve]
keep-alive = true
```

<Callout variant="note" title="Who can use it">
  The daemon listens on a unix socket only you can open. Anyone who can connect to it can act as you on every sandbox, like with `docker.sock`. Linux and macOS only.
</Callout>

## Talk to it

Editors and GUIs reach the same Inbox, instances and forwards as the dashboard through a JSON-lines API: spawn `devsandbox api --stdio`, or use the typed client of the npm package, `connect()`.
