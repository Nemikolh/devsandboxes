## Add a machine

```bash
devsandbox machine add me@my-server   # its config roots are the ones it lists
devsandbox run api                    # `api` is only defined there
devsandbox exec test                  # an instance there, over your daemon's link to it
devsandbox stop my-server/test        # qualified, when the name exists here too
devsandbox ps --machine my-server     # a command without a name, run there
devsandbox machine ls                 # each machine's state: connected, unreachable, …
```

- `machine add` offers to install this devsandbox there when it's missing or another version (`--auto-install` off a terminal), and asks you to confirm the machine's key fingerprint (`--yes`).
- Your ssh-agent reaches it only with `--agent`, or later `devsandbox machine set my-server --agent on` (`a` on the dashboard's Machines tab).
- `devsandbox port my-server/web 3000` opens a machine's port here. An `exec` there reconnects into the same session when the link drops.
- VS Code on a machine isn't supported yet.

<Callout variant="note" title="Adding a machine means trusting it">
  Whoever controls it can act as you in its sandboxes, and, with its `agent` on, sign with your ssh-agent while you use it.
</Callout>

## What a machine lends

Work placed on a machine gets nothing extra unless it allows it. Only that host sets its own allowances: `machine allow` there, or `machine add` over your ssh session to it.

```bash
devsandbox machine allow                                  # on the machine: list
devsandbox machine allow --gpus on --bind-add ~/datasets  # what placed work may use
devsandbox machine add box --allow gpus --allow-bind /srv/data   # or answer its prompt
devsandbox run ml --place                                 # a GPU sandbox goes to a machine lending one
```

`devsandbox machine trust full` on a machine opens its whole API to the fleet instead (any root, any path, `gc --machine`).

## A config every machine runs

A config can belong to the whole fleet, so an always-on server keeps running its sandboxes while the host it was written on is off. The fleet's authority (the host of its first `machine add`) signs a new version whenever a `run`, `rebuild` or `start` there finds the config changed, and every machine installs its own copy under `~/.local/share/devsandbox/mesh/tree/<root>/`. Edit the config on the authority: a copy changed in place is refused.

To run a config from your desktop on a server `box`, driven from your laptop:

1. Install the same devsandbox release on all three.
2. Desktop: `devsandbox machine add box --control-plane`; each signed root prints `note: signed config`.
3. Desktop, for another root or after an edit: any `run`, `rebuild` or `start` on it; a `note:` naming a machine says why it doesn't have it yet.
4. `box`: `devsandbox serve install`; a `run box/<sandbox>` from the desktop sends the repos, else clone them next to the copy; add the `${localEnv:…}` variables and logins the config needs.
5. Laptop: `devsandbox machine add box`, then `devsandbox run box/<sandbox>`.

## Control plane and versions

- `machine add box --control-plane` makes `box` the control plane of a new fleet; `devsandbox machine control-plane <m>` moves the role later, even off a dead one.
- Members run the build the authority pinned: a published release is downloaded and verified; a source build only with `dev-builds = true` in `member.toml` or `full` trust.
- `devsandbox machine upgrade <m>` copies this build over the machine's, over ssh.
- Links a sandbox on a machine opens open on the host that attached to it with a terminal last (within 10 minutes), in that host's [profile](/docs/going-further#links-open-on-your-desktop) browser.
