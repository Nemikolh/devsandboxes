## The problem

Parallel agents on one database step on each other: one runs a destructive migration while another's tests expect the old schema, one flushes Redis in the middle of another's run. For throwaway work each instance should own its backing services and be free to wreck them.

That is the default. A service without `scope` is **isolated**: every instance that lists it gets its own container, on a network private to that instance, under the same hostname. The config never changes, however many instances you run.

## Config

```toml title="config.toml"
[services.postgres]
image = "postgres:16"                  # scope defaults to "isolated"
env = { POSTGRES_PASSWORD = "postgres" }

[services.redis]
image = "redis:7"
command = ["redis-server", "--save", "", "--appendonly", "no"]

[sandbox.api]
folder = "../api"
image = "mcr.microsoft.com/devcontainers/base:ubuntu"
services = ["postgres", "redis"]
containerEnv = { DATABASE_URL = "postgres://postgres:postgres@postgres:5432/postgres", REDIS_URL = "redis://redis:6379" }
```

`command` is appended after the image: here Redis runs with persistence off, a pure in-memory cache. As an array each item is one argument; a plain string would be passed as a single argument, not split by a shell.

## Try it

```bash
devsandbox run api      # api, with its own postgres and redis
devsandbox run api      # api-2 on a worktree, with a second pair
devsandbox stats        # both instances and all four service containers
```

Each instance resolves the same names to its own containers:

```bash
devsandbox exec api getent hosts postgres redis
devsandbox exec api-2 getent hosts postgres redis   # different addresses
```

Services follow their instance: `devsandbox stop api-2` stops its postgres and redis too, `devsandbox start api-2` brings them back, and `devsandbox rm api-2` removes them along with the instance's network.

Change a service and apply it to every instance at once:

```bash
devsandbox service rebuild redis
```

This recreates the redis container of each running instance that uses it and rewires the instance in place; the sandboxes keep running. Stopped instances pick up the new container on their next `start`.

## How it works

- **Per-instance names.** An isolated service runs as `devsandbox-svc-<project>-<instance>-<service>` on the network `devsandbox-net-<project>-<instance>`. Both are keyed by the persistent instance id, so they survive a rename.
- **Same hostname everywhere.** The sandbox reaches each service by its name, through a network alias on docker and podman or an `/etc/hosts` entry on Apple `container`. That is why one `DATABASE_URL` works for every instance.
- **Mixing scopes.** A sandbox may list isolated and [global](/examples/shared-postgres) services together; the instance joins both its own network and the shared one.
- **Keys.** Services accept `scope`, `image` or `build`, `env`, `ports` and `command` ([services reference](/docs/config#services-servicesname)). A `build` service is rebuilt from its dockerfile by `service rebuild`, and editing the dockerfile marks it drifted ([drift](/docs/config#drift)).
- **Housekeeping.** `devsandbox gc` removes every service container no *running* instance references, and the networks of instances that are gone. That includes a stopped instance's services: its next `start` recreates them, empty.

<Callout variant="warning" title="No host ports on isolated services">
  A host port another container already publishes is an error, so `ports = ["5432:5432"]` on an isolated service
  breaks the second instance. Reach a single instance's service from the host with `devsandbox port` instead, on demand.
</Callout>
