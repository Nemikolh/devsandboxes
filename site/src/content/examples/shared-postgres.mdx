## The problem

Your API and your web app both need the development database, and so does every extra instance you spin up for an agent. Giving each its own Postgres means as many containers, migrations and seeds as instances, and data that differs between them.

A service with `scope = "global"` is created **once per config root** and shared by every sandbox that lists it.

<AgentPromptLink />

## Config

```toml title="config.toml"
[services.postgres]
image = "postgres:16"
scope = "global"                       # one container for the whole config root
env = { POSTGRES_PASSWORD = "postgres" }
ports = ["127.0.0.1:5432:5432"]        # optional: reach it from the host too

[template.base]
image = "node:22"
services = ["postgres"]
# The hostname is the service's name.
containerEnv = { DATABASE_URL = "postgres://postgres:postgres@postgres:5432/postgres" }

[sandbox.api]
extends = "base"
folder = "../api"

[sandbox.web]
extends = "base"
folder = "../web"
```

## Try it

```bash
devsandbox run api                     # starts postgres, then api
devsandbox run web                     # joins the running postgres
devsandbox run api --name fix-login    # its own worktree, same database
devsandbox service ls                  # one global postgres
```

- `--name`: the instance name.

Check an instance resolves the service, and connect from the host:

```bash
devsandbox exec fix-login getent hosts postgres
psql postgres://postgres:postgres@127.0.0.1:5432/postgres
```

## How it works

- Every instance that lists the service joins its network and reaches it by name ([services](/docs/config#services-servicesname)).
- `stop` and `rm` leave it running for the others; `devsandbox gc` removes it once no running instance uses it.
- `devsandbox service rebuild postgres` applies config changes and rewires running sandboxes in place ([drift](/docs/config#drift)).
- The data lives in the service container: `service rebuild` and `gc` start it empty, so keep a way to re-seed.
