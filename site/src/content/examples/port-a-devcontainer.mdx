## The problem

Your repo already has a `.devcontainer/devcontainer.json`, and you want to run it with devsandbox: several instances, worktrees, shared services, no devcontainer CLI. Rewriting it from scratch risks losing something; you want a mechanical translation and a clear list of what doesn't carry over.

`config.toml` uses the **same property names** as `devcontainer.json`, in TOML syntax, plus a few devsandbox extras. Most of a typical file moves over line by line. The differences: the config lives outside the repo, so `folder` says which repo a sandbox is for; a handful of properties are accepted but ignored; and compose-based setups become `[services.*]`.

## Config

The starting point, a common Node setup:

```jsonc title=".devcontainer/devcontainer.json (before)"
{
  "name": "web",
  "image": "mcr.microsoft.com/devcontainers/typescript-node:22",
  "features": {
    "ghcr.io/devcontainers/features/github-cli:1": {},
    "ghcr.io/devcontainers/features/docker-outside-of-docker:1": {}
  },
  "forwardPorts": [3000],
  "runArgs": ["--add-host=host.docker.internal:host-gateway"],
  "containerEnv": { "NODE_ENV": "development" },
  "mounts": ["source=${localEnv:HOME}/.config/gh,target=/home/node/.config/gh,type=bind"],
  "remoteUser": "node",
  "postCreateCommand": "npm ci",
  "postStartCommand": "npm run codegen",
  "customizations": {
    "vscode": {
      "extensions": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"],
      "settings": { "editor.formatOnSave": true }
    }
  }
}
```

The same sandbox in the config dir, next to the repo:

```toml title="config.toml (after)"
# Was web/.devcontainer/devcontainer.json. The table key replaces `name`.
[sandbox.web]
folder = "../web"                  # the repo; config.toml lives outside it
image = "mcr.microsoft.com/devcontainers/typescript-node:22"
remoteUser = "node"
containerEnv = { NODE_ENV = "development" }
mounts = ["source=${localEnv:HOME}/.config/gh,target=/home/node/.config/gh,type=bind"]
postCreateCommand = "npm ci"
postStartCommand = "npm run codegen"
# forwardPorts: gone, use `devsandbox port web 3000` when you need it.
# runArgs: gone, `--add-host` has no equivalent (and is rarely needed).
# settings: gone, keep them in the repo's .vscode/settings.json.
customizations.vscode.extensions = ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]

[sandbox.web.features]
"ghcr.io/devcontainers/features/github-cli:1" = {}
"ghcr.io/devcontainers/features/docker-outside-of-docker:1" = {}
```

Keys keep their names and values; JSON objects become inline tables or `[sandbox.web.features]` sub-tables, Feature options included. The three dropped properties would still be accepted if you left them in, with a warning at every `run`.

## Try it

Lay out the config dir next to your repo (`folder` is relative to the config dir):

```bash
mkdir devsandboxes && cd devsandboxes    # holds config.toml; ../web is the repo
devsandbox ls                            # validates every sandbox, no container needed
devsandbox run web
devsandbox exec -it web zsh
```

`ls` catches what doesn't translate: an unknown or misspelled key is a hard error naming it and listing every valid key, and so is a compose key. If you kept ignored properties, `run` says so:

```text title="devsandbox run web"
warning: ignoring unsupported properties: forwardPorts, runArgs, customizations.vscode.settings
```

Your `devcontainer.json` can stay in the repo for people using VS Code's Dev Containers or Codespaces; devsandbox never reads it.

## How it works

### Property mapping

| devcontainer.json | config.toml | notes |
|---|---|---|
| the file's location in the repo | `folder = "../web"` | devsandbox extra, required by `run` |
| `name` | the table key, `[sandbox.web]` | `name` itself is ignored |
| `image` | `image` | same |
| `build.dockerfile`, `build.context` | `build = { dockerfile, context }` | paths relative to the **config dir**, not to `.devcontainer/` |
| `build.args`, `target`, `cacheFrom`, `options` | same keys in `build` | same |
| `features` | `[sandbox.web.features]` | OCI references only |
| `containerEnv`, `remoteEnv` | same | `containerEnv` is not `${…}`-substituted |
| `containerUser`, `remoteUser` | same | `remoteUser` is also VS Code's attach user |
| `mounts` | same, string or table form | missing bind sources are created |
| `workspaceFolder` | same | default `/workspaces/<folder basename>`, as in VS Code |
| `workspaceMount` | `folder` | ignored: `folder` decides what is mounted |
| `init`, `privileged` | same | |
| `initializeCommand` | same | runs on the host, in the config dir |
| `onCreateCommand` … `postAttachCommand` | same | string, array or table form; tables run in order, not in parallel |
| `customizations.vscode.extensions` | same | |
| `customizations.vscode.settings` | repo `.vscode/settings.json` | ignored |
| `forwardPorts`, `appPort`, `portsAttributes` | `devsandbox port web 3000` | ignored; forward on demand |
| `runArgs`, `capAdd`, `securityOpt` | none | ignored |
| `dockerComposeFile`, `service`, `runServices` | `[services.*]` + `services` | **error** |

### Implemented, ignored, rejected

- **Implemented:** `image`, `build`, `features`, `workspaceFolder`, `mounts`, `containerEnv`, `remoteEnv`, `containerUser`, `remoteUser`, `init`, `privileged`, all six lifecycle commands, and `customizations.vscode.extensions` ([implemented properties](/docs/config#implemented-devcontainer-properties)). Exactly one of `image` / `build` is required.
- **Accepted but ignored** (a warning at `run`): `name`, `forwardPorts`, `appPort`, `portsAttributes`, `otherPortsAttributes`, `runArgs`, `workspaceMount`, `overrideFeatureInstallOrder`, `updateRemoteUserUID`, `userEnvProbe`, `overrideCommand`, `shutdownAction`, `capAdd`, `securityOpt`, `hostRequirements`, `waitFor`, `secrets`, `customizations.vscode.settings`, any other `customizations.vscode.*` key and any other `customizations.<tool>` ([accepted but ignored](/docs/config#accepted-but-ignored-warned-at-run)).
- **Rejected:** the compose keys `dockerComposeFile`, `service` and `runServices`, and any key devsandbox doesn't know. Unknown keys are errors so that typos surface immediately.
- **Variables:** `${localEnv:VAR}`, `${localWorkspaceFolder}`, `${localWorkspaceFolderBasename}` and `${devcontainerId}` work as in devcontainers, plus devsandbox's `${configDir}`, `${sharedVolumes}` and `${instance}`. They are substituted in `mounts`, `workspaceFolder`, `worktree-branch`, `shell-rc` and `folders`; anything else, like `${containerEnv:PATH}`, is left as written ([variables](/docs/config#variables)).

### Coming from docker compose

A compose-based devcontainer puts the app and its database in one `docker-compose.yml`. In devsandbox the app container is the sandbox, and each other compose service becomes a `[services.*]` table the sandbox lists by name; it is reachable under that name as hostname:

```toml title="config.toml"
[services.db]                      # was the `db` service of docker-compose.yml
image = "postgres:16"
env = { POSTGRES_PASSWORD = "postgres" }

[sandbox.web]
folder = "../web"
image = "mcr.microsoft.com/devcontainers/typescript-node:22"
services = ["db"]                  # replaces dockerComposeFile / service / runServices
containerEnv = { DATABASE_URL = "postgres://postgres:postgres@db/postgres" }
```

Services are isolated per instance by default, so every instance gets its own `db`; `scope = "global"` shares one. See [private services per instance](/examples/isolated-services) and [one shared Postgres](/examples/shared-postgres).

<Callout variant="tip" title="Several repos, one file">
  Port each repo's `devcontainer.json` into its own `[sandbox.*]` table, then pull what they share (user, Features,
  caches, mounts) into a `[template.*]` they `extends`. Tables merge recursively and arrays concatenate, so a sandbox
  only states what is its own.
</Callout>
