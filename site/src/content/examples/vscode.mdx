## The problem

An agent works in instance `web-3` and you want to read its diff, step through a test or poke at the running app in your editor. With several instances of one repo open, the windows all look alike, and an editor that attaches as the wrong user hits permission errors on the first save.

devsandbox wires VS Code's **Dev Containers** attach for you: one command (or `o` in the dashboard) opens a window attached to the instance's container, as the sandbox's `remoteUser`, with the sandbox's extensions, on a workspace named after the instance.

## Config

```toml title="config.toml"
[template.base]
customizations.vscode.extensions = ["editorconfig.editorconfig", "eamodio.gitlens"]

[sandbox.web]
extends = "base"
folder = "../web"
image = "mcr.microsoft.com/devcontainers/typescript-node:22"
remoteUser = "node"                # VS Code attaches as this user too
folders = { "/workspaces/design-system" = "../design-system" }
postCreateCommand = "npm install"
# Concatenated after the template's: all four get installed.
customizations.vscode.extensions = ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
```

`folders` adds `../design-system` (relative to the config dir) as a second root of the VS Code workspace, mounted at `/workspaces/design-system`. Drop it if one repo is all you need.

## Try it

You need VS Code with the **Dev Containers** extension (`ms-vscode-remote.remote-containers`) and `code` on your `PATH`.

```bash
devsandbox run web
devsandbox vscode web        # opening VS Code → web
devsandbox run web           # web-2, on its own worktree
devsandbox vscode web-2      # a second window, titled web-2
```

From the dashboard, select an instance and press `o`, or type `:code web-2`. Either way `code` is launched detached and the dashboard keeps running.

The window opens the workspace file `/workspaces/<instance>.code-workspace` inside the container: `workspaceFolder` first, then every `folders` root. VS Code titles the window after that file, which is how worktree instances stay tellable apart.

## How it works

- **Attach, not build.** VS Code doesn't create anything: devsandbox already made the container, and `code` is launched with a `vscode-remote://attached-container+<hex of the container name>/…` URI that opens it directly.
- **User and extensions.** For attached containers VS Code reads a per-container config from the Dev Containers extension's storage. devsandbox writes it at `run` and again on every attach, with [`remoteUser`](/docs/config#implemented-devcontainer-properties) and the merged `customizations.vscode.extensions`, for every installed VS Code, Cursor and VSCodium, so the editor attaches as `node` here and installs the four extensions in the container.
- **Extensions concatenate.** Arrays merge by concatenation under `extends`, so a template's extensions stay when a sandbox adds its own ([templates and `extends`](/docs/config#templates-and-extends)); the resolved list is visible in the dashboard's config explorer.
- **The workspace file.** `run` writes `/workspaces/<instance>.code-workspace` and rewrites it whenever the instance is reused, so older instances pick up new `folders`. Instances created before the file existed open their folder instead.
- **Worktrees and children.** Every instance attaches the same way, including worktree instances and a dispatcher's children like `web-pr-123` ([babysit pull requests](/examples/babysit-pr)).
- **Settings aren't applied.** `customizations.vscode.settings` and every other `customizations.vscode.*` key besides `extensions` are accepted but ignored, with a warning at `run` ([accepted but ignored](/docs/config#accepted-but-ignored-warned-at-run)). Keep editor settings in the repo's `.vscode/settings.json`: a tracked one is in every worktree, a gitignored one can be copied into them with `worktree-include`.

<Callout variant="warning" title="Apple container: experimental">
  On Apple `container` the attach goes through the Dev Containers extension's experimental support: set
  `dev.containers.experimentalAppleContainerSupport` to `true` in VS Code first (the status line reminds you). The
  per-container config is ignored there, so extensions are written into the workspace file as recommendations and VS
  Code offers to install them. Native Windows is untested.
</Callout>
