## The problem

Two agents in one checkout trip over each other: one switches branch while the other is mid-edit, one's `git stash` swallows the other's work, both run the dev server on the same files. You want one working tree and one branch per agent, and a container for each so their processes stay apart too.

That is what repeat instances do. The first `devsandbox run` of a sandbox mounts the repo itself; every further instance of the same repo gets its own **git worktree** under the config dir, on its own branch, in its own container. Gitignored files a fresh checkout lacks, like `.env`, are copied or linked in for you.

## Config

```toml title="config.toml"
[template.base]
remoteUser = "root"
caches = ["pnpm"]
persist-shell-history = true
[template.base.features]
"ghcr.io/devcontainers/features/node:1" = { version = "lts" }

[sandbox.app]
extends = "base"
folder = "../app"                      # the repo every agent works on
image = "mcr.microsoft.com/devcontainers/base:ubuntu"
worktree-branch = "agent/${instance}"  # default: sandbox/${instance}
worktree-include = [".vscode/settings.json"]  # copied into each worktree
worktree-link = [".env"]               # one .env, shared live by every instance
postCreateCommand = "pnpm install"
```

`folder` is relative to the config dir, so this assumes `app/` sits next to it. `worktree-branch` names the branch each worktree instance starts on; `${instance}` is the instance name at creation.

## Try it

From the config dir, start one instance per agent. `run` works in the background and prints only the instance name:

```bash
devsandbox run app --name claude   # first instance: mounts ../app itself
devsandbox run app --name codex    # worktree .worktrees/codex, branch agent/codex
devsandbox run app --name fix-login --branch fix/login --base origin/develop
devsandbox ps
```

- `--name` picks the instance name; without it you get `app`, then `app-2`, `app-3`…
- `--branch` overrides `worktree-branch` for that instance. An existing local branch is checked out as is, one that only exists on `origin` becomes a local branch tracking it, anything else is created. A branch already checked out in another worktree is an error that says where.
- `--base` is the start point of a new branch (default: the remote's default branch). It is ignored when the branch already exists.

Each agent then works through its own instance, or directly in its worktree on the host (`.worktrees/codex/` in the config dir):

```bash
devsandbox exec codex pnpm test
devsandbox exec -it codex zsh
```

When an agent is done, push its branch (see [ssh and git push](/examples/ssh-and-git-push)) and remove the instance:

```bash
devsandbox rm codex
```

`rm` deletes the container and the worktree. On a terminal it asks whether to delete the branch too, and only for a branch `run` created.

## How it works

- **When a worktree is made.** A new instance gets a worktree whenever some other instance, running or stopped, already mounts the repo. The two containers never share a working tree. The base repo's `.git` is mounted at its own host path, so git inside a worktree container works as usual.
- **Branch naming.** [`worktree-branch`](/docs/config#devsandbox-extras) accepts [`${…}` variables](/docs/config#variables) and defaults to `sandbox/${instance}`; [`worktree-base`](/docs/config#devsandbox-extras) sets the default start point. `run --branch` / `--base` override both.
- **Copied files.** A fresh worktree has no untracked files. A `.worktreeinclude` at the repo root (the convention Claude Code, Codex and others use) is always honored; `worktree-include` adds gitignore-style patterns from the config, applied after the file so `!pattern` can negate it. Only files git reports as ignored are copied, never overwriting, on `run` and again on every `rebuild` (not on `start`). Each worktree then owns its copy.
- **Linked files.** `worktree-link` is for files every instance should see live, like `.env`. The base repo's file is moved to `shared-files/app/` in the config dir, each tree gets an absolute symlink to it, and that directory is mounted at its host path so the links resolve inside containers too, on every runtime. Tracked or non-ignored paths are skipped with a warning. The store is kept on `rm`.
- **Arrays concatenate.** Put `worktree-include` / `worktree-link` in a template and every sandbox extending it inherits them, adding its own entries ([templates and `extends`](/docs/config#templates-and-extends)).

<Callout variant="tip" title="Where the agent runs">
  An agent can run on the host and drive its instance with `devsandbox exec` (the `devsandbox-cli` skill teaches it
  exactly that), or run inside the container when the image has it installed. Either way it edits its own worktree.
</Callout>
