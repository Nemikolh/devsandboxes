Each host process that wants to reach a container runs its own `devsbd bridge` there. The bridge is a pipe fitter:
it does a handshake on each side, then copies bytes until either end closes. All the logic is in the shared
`Mux` (`src/devsbd/mux.rs`), which runs in the daemon and on the host, so only those two ends parse frames.

## Two handshakes

The bridge sends `Hello` to the daemon first, then to the host. So a daemon of another protocol version fails the
bridge (exit `3`, `proto::MISMATCH_EXIT`) before the host sees a frame, and the host never sends frames the
daemon can't parse. Only `VERSION` must match. The build hash in `Hello` is informational: a bridge and daemon of
the same old build work with a newer host as long as the protocol is the same.

The caps don't pass through on their own, since each side only sees its own handshake:

- the daemon's `Hello` advertises what it serves (`TCP_FORWARD`),
- the bridge tells the host `OWN_CAPS ∧ daemon caps`, so a forward isn't attempted against a daemon that can't
  serve it,
- the host then sends `Caps` with what *it* serves, and the bridge passes it through unchanged. `SSH_AGENT` only
  when it has a live agent, `NOTIFY` and `CONTROL` only from the host daemon's instance bridge (the one with a
  sink).

A host whose `Hello` mismatches (either side) retries that container every 5 minutes instead of every 10 s: only
a helper rewrite fixes it.

## Frames

One byte stream each way, little-endian, each frame written with a single `write_all` so writers can share it:

```text title="src/devsbd/proto.rs"
u32 stream_id | u8 kind | u32 len | payload[len]      (len ≤ 1 MiB)
```

| kind | name | stream | payload |
|---|---|---|---|
| 0 | `Hello` | 0 | `u32 version`, `u8` + build hash, `u32 caps` |
| 1 | `Open` | daemon id | `u8 channel`: 1 ssh-agent, 2 http-proxy (reserved), 3 notify, 4 control |
| 2 | `Data` | any | bytes |
| 3 | `Close` | any | optional reason (`connection refused`, …) |
| 4 / 5 | `Ping` / `Pong` | 0 | echoed |
| 6 | `Quit` | 0 | none: the daemon takeover |
| 7 | `Connect` | host id | `u16 port`, `u8` + host |
| 8 | `Window` | any | `u32 credit` (flow control on `Connect` streams) |
| 9 | `Eof` | any | none: half-close |
| 10 | `Caps` | 0 | `u32` host caps |

The header, `Hello`'s leading `version` and `Quit` are frozen forever, so any two builds can at least report a
mismatch and evict each other. Unknown kinds are skipped (payload consumed). That's how 7–10 landed without a
`VERSION` bump.

**Stream ids.** The daemon allocates ids with the high bit clear (agent, notify and control streams it opens),
the host with it set (`Connect`). Each side refuses the other's id space, a live id, or too many streams: 64
daemon streams per bridge on the host, 256 `Connect` streams in the daemon.

## Routing in the daemon

The daemon keeps every attached bridge, newest last, and routes each kind of stream on its own:

| stream | goes to | when there's none |
|---|---|---|
| ssh-agent | newest bridge whose host advertised `SSH_AGENT` | held up to 1 s for one, then closed ("agent refused") |
| notify | newest bridge with `NOTIFY` | stays in `/var/lib/devsandbox/outbox/`, retried every 30 s and on attach |
| control | newest bridge with `CONTROL` | answered `NoHost` (the CLI exits 75) |
| `Connect` | n/a: opened by the host | |

A bridge whose `Caps` hasn't arrived yet counts as not capable, unless its `Hello` caps were 0 (a host from
before caps). So an agent-less `devsandbox port` that attaches last can't take ssh away from the host daemon's
bridge.

## Takeover

`start` on a running container after a CLI upgrade rewrites the binary and starts a daemon of the new build. The
last start wins, upgrade or downgrade:

Same build hash → the second daemon exits 0. No hash in the pidfile yet (its owner is still starting) counts as
the same build, so two concurrent starts never evict each other.
