devsandbox already brokers one credential well: the ssh-agent. A sandbox never sees a key; it gets a socket, the
request crosses the helper bridge, and the host signs. Everything else (gh, sentry-cli, zidane's login, MCP OAuth
tokens) is a file bind-mounted into every sandbox. That leaks every token to every sandbox, ignores profiles, and
stops at the machine's edge: a sandbox placed on another machine starts logged out.

This page proposes doing for every credential what the relay does for the agent, plus the part the agent lacks:
per-sandbox permissions.

<Callout variant="note" title="A proposal, nothing here is built">
  Unlike the other architecture pages this one describes a design, not the code. Config and manifest blocks are
  sketches and don't parse today. It supersedes the earlier CLI-shim plan (`cli-proxy`).
</Callout>

## What goes wrong today

| threat | today | wanted |
|---|---|---|
| a sandbox reads a token (`cat ~/.config/gh/hosts.yml`) | the real token, valid anywhere | a phantom, useless outside its own instance |
| a sandbox uses gh on a repo it isn't about | allowed, all your repos | denied: only the repos of its `folder` and `folders`, more only by config |
| `git push` from a sandbox meant to be read-only | allowed | refused per sandbox; per branch when the config says so |
| sentry-cli in a `personal` sandbox | allowed | the credential isn't granted to that profile |
| a sandbox on another machine | logged out, or a second copy of every token | works, no long-lived secret leaves home |
| one compromised sandbox | holds every credential every sandbox has | holds none; can misuse its own scope while running |

The last row is the honest limit: a sandbox allowed to open PRs on `acme/web` can open a bad one. The goal is to
make that the *whole* damage, not "your GitHub account".

## What Kubernetes does

Kubernetes grew from handing secrets to workloads toward handing them identities. Its older answers are what devsandbox
does now; its newer ones are what this page borrows.

| Kubernetes | what it does | lesson for devsandbox |
|---|---|---|
| `Secret`, as env or a tmpfs volume | the value lands in the pod; anyone who can `exec` reads it | today's bind mounts. Avoid. |
| ServiceAccount, projected bound tokens (TokenRequest) | each pod gets an identity token with an audience and an expiry, bound to that pod | each instance gets an identity; phantoms bound to it |
| RBAC on secrets, Node authorizer + NodeRestriction | a kubelet can only read secrets of pods scheduled on its node | a member only gets credentials for instances it runs, and only what the home grants it |
| admission (Pod Security, Kyverno, Gatekeeper) | policy checked before a pod runs | `run` checks what a sandbox asks for against the grants, and says no up front |
| Secrets Store CSI driver, External Secrets | values come from Vault, cloud KMS, 1Password, not etcd | pluggable sources behind one store |
| workload identity (EKS Pod Identity, GKE) | a local endpoint exchanges the pod's identity for short-lived cloud credentials | mint narrowed tokens per instance, renewed out of the tool's sight |
| service mesh egress (Envoy credential injection, Istio egress gateway), NetworkPolicy | the sidecar adds credentials and limits egress; the app never sees them | the helper plus the host daemon are already that sidecar |

What Kubernetes never solved for us: its identities authenticate the *workload to the cluster*, and to clouds that
accept its OIDC tokens. GitHub, Sentry and model providers don't, so something has to hold a user's token and act for
the workload. In a mesh that's an egress proxy. In devsandbox it's the host daemon, which already sits on every
instance's only path out (the bridge).

## Thinking it through

The design below came out of three passes (Boden's combinational, exploratory and transformative creativity, as in
the Universe of Thoughts framework): combine mechanisms from other fields, push past the obvious boundaries, then
question the rules themselves. Ideas are scored for utility and novelty (1–10); infeasible ones are dropped.

### The assumptions under the problem

| assumption | type | if dropped |
|---|---|---|
| the process calling the API must hold the token | assumption | an egress broker swaps a placeholder for the token |
| a credential is one token, shared by everything that uses it | convention | a handle per instance that lives until `rm`; behind it, a narrowed token the broker mints and refreshes |
| policy is about CLI subcommands (`gh pr *`) | assumption | policy is about API routes, which every client shares |
| credentials live where the sandbox runs | convention | they live at a *home* and are reached over the fleet |
| a tool must be "logged in" inside the sandbox | assumption | it only needs to *believe* it is |
| ssh is the git transport | convention | smart HTTP exposes repo, service and refs to a broker |
| devsandbox must understand every tool | assumption | features describe their tool; devsandbox runs the mechanism |

### Combinational: mechanisms from elsewhere

| idea | borrowed from | gives | U | N | U×N |
|---|---|---|---|---|---|
| egress broker with phantom tokens | Envoy credential injection + Fly.io's tokenizer + the helper's reserved `HTTP_PROXY` channel | no token in the sandbox, policy per HTTP route, any language | 9 | 6 | 54 |
| ask on first use | mobile runtime permissions + the dashboard's modals | out-of-scope calls become a question, not a failure | 7 | 7 | 49 |
| mint, don't share | GitHub App installation tokens + bound ServiceAccount tokens | the upstream itself enforces repo and permission limits | 8 | 6 | 48 |
| credentials follow placement | NodeRestriction + the fleet's `[[agent]]` grants | remote sandboxes work; members hold only what they need | 8 | 5 | 40 |
| CLI shims with an argv policy | the earlier cli-proxy plan | gh and sentry-cli only; no git, no SDKs | 5 | 3 | 15 |
| `LD_PRELOAD` / ptrace interception | debuggers | fails: gh is static Go, and it's a network-filesystem project | — | — | fail |

### Exploratory: past the boundaries

| boundary | probe | idea | U | N | U×N |
|---|---|---|---|---|---|
| git over ssh hides the repo and refs | what does smart HTTP show? | a git gateway reading `git-receive-pack` commands: read-only sandboxes, branch rules where configured | 9 | 8 | 72 |
| rules are static lists | what does the broker know about the caller? | the sandbox's repos as the default fence, rules over instance context (`${instance}`, profile) | 8 | 7 | 56 |
| the home must be online | what can a member hold safely? | delegation of mintable credentials: the app key stays home, an expired token costs one hop back | 8 | 6 | 48 |
| interception needs a CA | which tools take a base URL? | base-URL mode (`SENTRY_URL`, `ANTHROPIC_BASE_URL`) first, TLS interception only where needed | 7 | 5 | 35 |
| a grant is forever | what does sudo do? | time-boxed grants, an audit line per call | 6 | 5 | 30 |
| the ssh-agent signs anything for anyone | what can a relay see? | per-sandbox key filtering and confirm-on-sign; never per repo | 6 | 4 | 24 |

### Transformative: changing the rules

| rule | becomes | idea | U | N | U×N |
|---|---|---|---|---|---|
| sandboxes hold credentials | sandboxes have identities | every brokered call is (instance identity, credential, route); devsandbox could later issue OIDC tokens for services that accept them | 9 | 8 | 72 |
| the agent is part of the sandbox | the agent is a principal | zidane acts under its instance's identity; marked routes need a human even when allowed | 8 | 8 | 64 |
| devsandbox knows the tools | features describe the tools | a claim contract in `devcontainer-feature.json`; devsandbox owns the mechanism, like a CSI driver and its plugins | 9 | 7 | 63 |

### The portfolio

- **Low risk**: the egress broker in base-URL mode for sentry-cli and model APIs, rules on routes, profiles gating
  grants. Reuses the reserved channel and the bridge.
- **Medium risk**: TLS interception for gh, the git gateway, permission requests, routing to the home over the fleet.
- **High reward**: instance identity as the unit of policy, minted tokens, the feature claim contract, delegation.

## The proposal: identities, not credentials

1. **Nothing secret enters a container.** A tool gets a *phantom* (`dsbx_github_…`): shaped like a token, bound to one
   instance, worthless anywhere else. Its traffic goes to the helper's loopback listener and over the bridge.
2. **The bridge is the identity.** A stream on an instance's bridge comes from that instance; the sandbox can't claim
   to be another one. Across machines the instance's host signs that claim with its member key.
3. **A credential has a home.** The member where you logged in holds it and decides who may use it
   (`credentials.toml`, read only there), as `profiles.toml` decides openers (ADR 0048): a config can ask, only the
   home grants. The authority's membership log names the home, so no member can make itself one. Log in on an
   always-on member for credentials remote sandboxes use.
4. **Policy is on routes, named by the feature, chosen by the sandbox, capped by the home.** Effective access is
   `grant ∩ access ∩ scope table`.
5. **Narrow at the source when possible.** Where the upstream can mint (GitHub Apps, cloud STS), the injected
   token is itself limited; the broker's rules are the second fence, not the only one.
6. **A tool never sees an expiry.** Its phantom lives until the instance is removed; whatever the upstream token's
   life, the broker renews it behind the phantom while the request waits.

Most of the identity already exists: every instance has an `instance_id`, every member a key the fleet authority
signed, and every stream from a container arrives on that instance's own bridge. What's missing is the claim a
member signs for its instance (instance, sandbox, profile, repos) and a home that checks it.

## Lifetimes

Regenerating tokens isn't the point; *where a token can be used, and by whom* is. So lifetimes depend on where the
secret sits, and nothing a tool holds ever expires under it:

| what | lives | why |
|---|---|---|
| the phantom, in the sandbox | until `rm`; no expiry | revoked with the instance; a copy taken elsewhere is useless anyway |
| a credential at its home | as long as you keep it | never leaves the home, so expiry buys nothing |
| a token the home mints for the broker on the same host | as long as the upstream allows (GitHub App tokens: 1 h, fixed) | renewed behind the phantom |
| a token delegated to another member | the same, at most | the backstop for a member that dies or is compromised before any `rm` reaches it |

That last row is the only real reason for expiry: revocation at `rm` assumes the member holding the token is still
there to drop it. For an agent, expiry costs a hop, never a failure:

<Sequence title="A delegated token expiring mid-task" lanes={s.expiryLanes} steps={s.expirySteps} />

Delegation needs a credential the home can *narrow*. GitHub can (App installation tokens per repo set and permission
set). A Sentry token, a model API key or a subscription's OAuth access token can't: delegating one would copy it.
Those are always brokered from home. GitHub alone justifies building
delegation; the rest can wait for a provider that mints.

TLS ends at the instance's host, with a CA per member whose key never leaves it; the home makes the upstream call,

plain HTTP to `127.0.0.1`, TLS only from the broker out. Hosts no claim names never reach the broker: the helper
dials them from the container, as before.

## The policy

Each brokered call walks the same steps, in order; the first refusal answers.

<States title="Deciding one brokered call" states={decision} />

The three inputs live in three places, and each can only narrow the others.

The home's grants, next to `state.toml` on the member holding the credential:

```toml title="credentials.toml (sketch)"
[github]
source = "file"                   # 0600 beside member.key; the keyring on macOS; or "op://Private/github/token"
as = ["app", "user"]              # token kinds offered: installation tokens minted per instance, or yours
profiles = ["work", "personal"]
members = ["box"]                 # who may broker it, like [[agent]] grants
approvers = ["laptop"]            # who may answer its permission requests
delegate = ["box"]                # who may hold minted tokens itself
max = ["repo.read", "pr.write", "issues.write", "git.push"]
# plus the approved claim versions and the rules, written by login, access approve and your answers

[sentry-work]
source = "file"                   # an internal-integration token
profiles = ["work"]               # personal sandboxes never see it
```

What a sandbox asks for, in the config (shared, signed by the fleet authority, possibly not yours):

```toml title="devsandboxes.toml (sketch)"
# The repos are implicit: every remote of folder and folders, recorded at the folder's first run.
[template.base.access.github]
scopes = ["repo.read", "pr.write", "git.push"]
ask = ["issues.write"]               # held for you to answer, not denied

[sandbox.web.access.github]
repos = ["acme/design-system"]       # one more repo: only ever by config

[sandbox.untrusted.access.github]
scopes = ["repo.read"]               # git push answers 403

[sandbox.release-bot.access.github]
branches = ["release/*"]             # opt-in; no branch rule by default

[sandbox.web.access.sentry]            # the kind: work sandboxes get sentry-work
scopes = ["releases.write", "issues.read"]
```

The repos are the fence. A sandbox reaches the repos its checkouts point at (every remote, so a fork and its
upstream both count) and nothing else: another repo gets no credential, never an ask, and only a config change adds
one. The remotes are read once, at a folder's first `run`, since the checkout's `.git/config` is writable from the
container. Outside the fence a request goes upstream as a stranger's: public repos still work. With a minted token
GitHub enforces the fence itself, which matters for the routes a broker can't attribute to one repo: search, GraphQL
queries, notifications. Branches are free by default, since one sandbox often opens many PRs; `branches` narrows
them when you want it.

| who | can widen | can narrow |
|---|---|---|
| the home (`credentials.toml`) | grants, members, `max` | everything |
| the config (`access`) | extra repos, up to the grant | scopes, branches, ask vs deny |
| the feature (scope table) | nothing: names routes only, and the home pins the version it approved | which routes a scope covers |
| you, answering a request | an `ask` scope, once, per instance, or as a rule | denials are remembered too |
| signed policy from the authority | rules that answer requests, if the home opts in | anything |
| the container | nothing | nothing |

## Permission requests

Unattended agents hit the edge of their scope all the time. Rather than a bare 403, an `ask` scope holds the request
(for the claim's `hold`) and raises a permission request on the home and its approvers: a modal in the dashboard, a
desktop popup, and `devsandbox access pending|approve|deny` (the shape `machine pending|approve|deny` already has for
membership). Asks never cross the repo fence; they negotiate verbs inside it. Routes a claim marks `presence` (a
release, a tag push, a branch deletion) always ask, even when allowed, and only you answer them, once or for this
instance on that one target.

<Sequence title="A held call, answered" lanes={s.askLanes} steps={s.askSteps} />

This is the part of the Inbox worth keeping, as its own thing: a queue of decisions only you can make, each with an
expiry, not a feed. On top of it, rules in three layers, each only answering what the layer above left open:

1. **Remembered answers.** "Always" writes a rule into the home's `credentials.toml`, listed and revocable.
2. **Your rules.** Written by hand in the same file: auto-approve `issues.write` for `profile = "work"`.
3. **Signed policy.** Rules the fleet authority signs and every member installs, like configs (ADR 0049). A home
   applies them only if it opts in, and only within its own grants: the authority can't hand out your credentials.

No layer answers a `presence` request or lifts a budget.

## Git

The ssh-agent can't tell `git push acme/web` from `git push acme/infra`: the repo path and refs travel inside the ssh
session, and the agent only sees a signature request. Smart HTTP shows all of it, so git reaches `github.com`
through the same intercept as gh, on a proxy port of its own (ssh remotes rewritten to `https://github.com/`, so `git remote -v` still shows
GitHub) and the broker reads the pushed ref names (not the objects) before anything goes upstream:

<Sequence title="A push to main, refused per branch" lanes={s.gitLanes} steps={s.gitSteps} />

The example sandbox opted into a branch rule; by default any branch of a linked repo can be pushed, and a read-only
sandbox is refused at `info/refs`, before git sends anything.

### One clone per instance

The gateway also changes what a checkout should be. Today a repeat instance gets a git worktree, whose `.git` file
points into the main checkout, so that checkout's `.git` is mounted into the container too: a git directory several
sandboxes write to, with refs, config and lock files any of them can touch, and quirks even read-only. With a gateway
there is a better default: every repeat instance gets its own full clone, seeded from your checkout and
upstream.

- **Seeded locally**: each clone (a full copy) gets your checkout's branches and tags, bundled in a container so host
  git never opens a sandbox-writable `.git`, plus a fetch from upstream with that instance's credential before its container starts.
- **Fetches and pushes go upstream** through the gateway: `upload-pack` checked against the fence, `receive-pack`
  against the push rules.
- **No shared git directory**: each clone has its own `.git`, most likely in a host dir as worktrees are today, so
  host editors keep working.
- **Local and remote converge**: an instance on B fetches upstream into its clone where its credential is delegated to B,
  else starts from the bundle.

What it costs: disk (a full copy per instance), and a clone's unpushed commits no longer land in your checkout, so
dispatcher children move to clones only once a per-instance local remote on the host takes their commits. The git
plan covers it, starting from a list of today's worktree problems.

The agent relay stays for ssh to named destinations and for hosts with no broker claim. Under a git-host claim it
filters keys: only the keys the sandbox's config names, each bound to its destinations (host keys from the host's own
`known_hosts`) or signing-only for commit signatures, so the sandbox can't reach GitHub around the gateway with your
key. Confirm-on-sign comes later, as an ask. VS Code's attach forwards the host's git credentials and agent on its
own, so it stays outside the guarantee and `devsandbox vscode` warns.

## Tool by tool

| tool | reaches the broker by | rules see | narrowed at the source |
|---|---|---|---|
| gh | `HTTPS_PROXY` + member CA, phantom `GH_TOKEN` and `hosts.yml` | REST method + path, GraphQL mutations and the repos their inputs name | GitHub App installation token: its repos, its permissions |
| git (HTTPS) | the same intercept for `github.com`, ssh forms rewritten to https, devsbd as credential helper | repo, `upload-pack` vs `receive-pack`, ref names | the same installation token |
| git / ssh | the agent relay | which key, bound to which destinations | ssh certificates, if you use them |
| sentry-cli | `SENTRY_URL=http://127.0.0.1:…`, phantom `SENTRY_AUTH_TOKEN` | org, route | an internal-integration token per org, granted per profile |
| zidane, model SDKs | the provider's base URL, phantom API key | model, route; tokens counted | budgets per instance and profile |
| MCP servers over HTTP | intercept, one generic `mcp` claim per granted server; OAuth done at the home | server, tool | per-server OAuth scopes |
| npm, PyPI, cargo registries | registry URL, phantom in `.npmrc` | package, publish vs read | publish tokens never granted by default |
| AWS, GCP | the container credential endpoint (`AWS_CONTAINER_CREDENTIALS_FULL_URI`) | role per profile | STS: short-lived, the role's policy |

## Trusting the CA

Interception only works if every client in the container trusts the member CA (ECDSA P-256: browsers and other
verifiers refuse Ed25519 certificates), so that's devsandbox's job, not each feature's: at create it adds the CA to
the image's system bundle (`update-ca-certificates` or the distro's equivalent) and sets the common variables on the
container env. Some variables *add* to the defaults, others *replace* them, so the replacing ones point at the
system bundle file itself, never at the CA alone or a snapshot.

| client | reads | devsandbox sets |
|---|---|---|
| Go (gh, most static CLIs), OpenSSL, curl | on Linux, the system bundle | nothing more; no custom gh build needed (no `SSL_CERT_FILE`, which would replace it) |
| git | libcurl's bundle, unless `http.sslCAInfo` says otherwise | `http.https://github.com/.sslCAInfo` = the system bundle |
| Node, Bun | their own roots; `NODE_EXTRA_CA_CERTS` adds | `NODE_EXTRA_CA_CERTS` |
| Python requests, certifi, AWS SDKs | certifi's roots; `REQUESTS_CA_BUNDLE`, `AWS_CA_BUNDLE` replace | both = the system bundle |
| Deno | `DENO_CERT` adds | `DENO_CERT` |
| Java | its truststore, and it ignores `HTTPS_PROXY` | nothing: base-URL mode only |
| Rust with roots compiled in (`webpki-roots`), pinned certificates | nothing | can't intercept: base-URL mode or none |

The CA carries X.509 name constraints listing only the hosts some claim intercepts (`api.github.com`, …), so even a
leaked key couldn't impersonate any other site. Go and OpenSSL enforce them. A claim for a new host reissues the
cert over the same key, reinstalled in place: no drift.

## zidane and other agents

zidane is the trickiest case, and gets a plan of its own. It's three things at once:

- **A tool with its own login.** Its model credential is an API key, brokered like any other: base URL to the
  helper, a phantom key on the container env, an always-on home. With subscription OAuth the home keeps
  the refresh token and answers the client's
  own refresh with the phantom. A remote sandbox needs nothing logged in: the fix for "not logged in on B". OpenAI
  stays unavailable in sandboxes until brokered.
- **A principal acting with everything else.** Every gh, git or sentry call zidane makes goes through the same
  broker under its instance's identity, so it can't do more than the sandbox may; `presence` routes and ref pushes
  ask a human even when allowed. Nothing it runs or that steers it is shared writable: its binary and skills are
  read-only, its settings and state per instance, no config root is mounted, and it never asks you for a secret.
- **A client of asks.** An agent is the one most likely to hit an `ask`. Refusals come in the upstream's own error
  shape with the reason and what to do; a held model call looks like the provider being overloaded (`529`), so the
  SDK retries into the answer. zidane can wait on a request its instance raised with `devsbd access wait`.

MCP servers get one generic `mcp` claim per server the config grants, its URL bound at the home's login, with OAuth done there. A server
fronting a fenced credential (GitHub's, Sentry's) is refused there: it can only come through its tool's claim.

What a broker can't do: stop an agent from leaking what it legitimately *read* through a route it may *write*
(code into a PR body, for example). That's prompt injection and exfiltration inside the scope; egress lists and
narrow scopes shrink it, they don't close it.

## Who owns what

The split that keeps devsandbox small and features easy to write: the feature knows its tool, devsandbox knows
identity, policy and transport, and neither knows the other's details.

<States title="Ownership, from the tool down" states={ownership} />

A feature declares its claim as data, next to its install script:

```json title="devcontainer-feature.json (sketch)"
{
  "id": "gh",
  "customizations": {
    "devsandbox": {
      "credentials": {
        "github": {
          "upstreams": ["api.github.com", "uploads.github.com", "github.com"],
          "inject": { "header": "Authorization", "format": "token {token}" },
          "mode": "intercept",
          "phantom": { "env": ["GH_TOKEN"], "files": ["~/.config/gh/hosts.yml"] },
          "git": { "https": ["git@github.com:", "ssh://git@github.com/"], "helper": true },
          "login": ["app-manifest", "paste"],
          "mint": "github-app",
          "scopes": {
            "repo.read": ["GET /repos/{repo}/**", "git-upload-pack {repo}"],
            "pr.write": ["POST /repos/{repo}/pulls", "PATCH /repos/{repo}/pulls/*", "graphql mutation createPullRequest"],
            "issues.write": ["POST /repos/{repo}/issues", "graphql mutation createIssue"],
            "git.push": ["git-receive-pack {repo}"]
          },
          "fence": { "createPullRequest": ["repositoryId", "headRepositoryId"], "createIssue": ["repositoryId"] },
          "presence": ["DELETE /repos/{repo}/git/refs/{ref}", "POST /repos/{repo}/releases", "git-receive-pack refs/tags/**"],
          "never": ["POST /repos/{repo}/keys", "POST /repos/{repo}/hooks"],
          "hold": "120s",
          "refusal": "github"
        }
      }
    }
  }
}
```

Why this split:

- **Features stay plain devcontainer features.** Outside devsandbox the claim is ignored and the tool logs in as
  usual. `ghcr.io/devsandboxes/features/gh` and `/sentry` are an install script plus a table.
- **No host code from a feature.** A claim can't run anything on the home or a member; it names routes. Minting
  adapters (GitHub App, OAuth refresh, STS) are a small fixed set in devsandbox. The home pins the claim it
  approved, so a new feature version that changes it waits for `devsandbox access approve`.
- **One mechanism to secure.** The CA, the identity, the policy engine and the store are written once. A new tool
  costs a table, not a security review of a new proxy.

## Open questions

- **Outside the fence.** The plans read "other repos are denied" as "no credential": the request still goes out
  anonymously. Or refuse it outright?
- **GraphQL under your own token.** Mutations name their repos and are fenced; queries can't be. Under an app user
  token or a fine-grained PAT their reach is the token's, not the sandbox's: accept that, or keep user tokens off
  queries, which is most of gh?
- **Upgrades mid-stream.** A daemon handoff or a helper upgrade cuts open streams (a model's answer, a long push, a
  held ask) unless the old one may finish them.
- **Off unix.** Like the relay, the broker lives in `serve`; Windows hosts get none until the daemon runs there.
