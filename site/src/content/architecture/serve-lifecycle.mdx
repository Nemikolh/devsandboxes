`devsandbox serve` is the per-user host process that owns the live host side: the bridges, the Inbox sink, the
port forwards and the API. Nobody is expected to run it by hand. Commands start it on demand, it exits once
nothing needs it, and a newer binary replaces it on first contact. Unix only.

## Lazy start

`serve::client::connect` sends a `hello` and, if nothing answers, starts a daemon and polls for 5 s. Here's an
`exec` into a relay-mode instance with an ssh-agent in the shell:

<Sequence title="exec, with no daemon running" lanes={startLanes} steps={startSteps} />

Without a unit, the child is `devsandbox serve --socket-dir <dir>` in its own session (`setsid`), so the
terminal's hangup and Ctrl-C don't reach it. A thread in the client reaps it if it exits while the client lives on
(the dashboard). With a unit installed (`serve install`), the start goes through the service manager, and the
daemon gets the manager's environment plus what `install` captured (`PATH`, the runtime, `XDG_*`; never
`SSH_AUTH_SOCK`, which clients report per request).

## Who talks to the daemon

| client | how | starts one | holds it |
|---|---|---|---|
| dashboard | `connect` at launch, reconnect with backoff, `instances.watch` on it; plus a procs connection and one per verb request | yes (the procs one doesn't) | while open |
| `run`, `start`, `rebuild`, `stop`, `rm`, `service rebuild` | a verb request on its own connection | yes | until the answer (`-d`: until registered); the verb itself holds it until it exits |
| `run`'s, `start`'s, `rebuild`'s lifecycle commands | `bridges.ensure` with `wait: 12` | yes | for the chain |
| `exec` | `bridges.ensure` on a thread, no wait | yes | while the command runs |
| a dispatcher's child op | the daemon itself, over its own socket: `connect_running`, then `bridges.ensure`, waited, no agent reported | no (a draining daemon must not start another) | for the op |
| `api --stdio` | byte relay to `serve.sock` | yes | while it runs |
| `inbox` mutations | `connect_running`, else the same op locally | no | for the call |
| `serve install` | `connect_running`, then `shutdown` | no | no |
| `devsandbox port` | none: forwards in its own process | no | no |
| `machine add\|ls\|set\|rm`, a command naming a machine's instance or given `--machine` | `connect`, then `machines.*` / `instances.resolve`; a remote match runs as API calls and `PTY` dials over the machine's link | yes | for the lookup |
| another host's daemon (a machine link) | `ssh … devsandbox fleet-link --peer <host>` here, each stream a `link.attach {channel}` connection, hello as `0.0.0` (never a handoff) | yes, `links.inbound` | for the link's life (that host's daemon holds it while it runs); `machine add`'s probe is `api --stdio --sentinel` once |

The `bridges.ensure` rows only happen for relay-mode instances when the caller's shell has a live ssh-agent;
otherwise those commands never contact the daemon.

## Handoff

A client whose `hello` is newer than the daemon's (`build` is the binary's mtime, so a rebuilt dev binary
counts) makes the old one step aside:

<Sequence title="A newer build taking over" lanes={handoffLanes} steps={handoffSteps} />

With a unit installed, the client rewrites it from its own binary and environment and restarts it, so the managed
daemon follows upgrades. If the unit's binary is gone (a Homebrew `Cellar` path, an npm reinstall), the next
start repairs it. Known gap (`client.rs`): if an older client's daemon wins the lock race, the newer client gives
up after its 5 s and hands off again on its next call.

## Exit

Idle, handoff and `shutdown` all leave the same way: the listener goes first (so a successor waits for the lock
instead of seeing a live daemon), then `closing`, the 5 s drain, the machine links (their ssh killed: a remote verb
not sent `detach` is cancelled there), the bridges and the forwards, and the lock last.
`serve uninstall` is the exception: the manager signals the daemon, so clients see the socket drop with no
`closing` and reconnect by starting one on demand.
