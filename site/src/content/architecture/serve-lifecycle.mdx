`devsandbox serve` is the per-user host process that owns the live host side: bridges, the credential broker, the
Inbox sink, port forwards, verbs, feature updates, machine links and the API. Commands start it on demand, it exits once nothing needs it, and a newer
binary replaces it on first contact. Unix only.

## Lazy start

`serve::client::connect` sends a `hello` and, if nothing answers, starts a daemon and polls for 5 s. Here's an
`exec` into a relay-mode instance with an ssh-agent in the shell:

<Sequence title="exec, with no daemon running" lanes={startLanes} steps={startSteps} />

Without a unit the child runs in its own session (`setsid`), out of reach of the terminal's hangup and Ctrl-C.
Every fd above stdio is marked close-on-exec first, so a pipeline whose command starts the daemon still ends. With
a unit (`serve install`), the start goes through the service manager, with the environment `install` captured.

## Who talks to the daemon

| client | how | starts one | holds it |
|---|---|---|---|
| dashboard | `connect` at launch, reconnect with backoff, `instances.watch`; plus a procs connection and one per verb request | yes (not the procs one) | while open |
| `run`, `start`, `rebuild`, `stop`, `rm`, `service rebuild` | a verb request: the daemon runs it as a `devsandbox --in-process` subprocess and streams it back | yes (none reachable: runs in the CLI) | until the answer (`-d`: until registered); the verb holds it until it exits |
| `exec` | `bridges.ensure` on a thread, no wait | yes | while the command runs |
| a TTY `exec`, a dashboard terminal | `instances.attach`, hello as `0.0.0` (where the instance's opened URLs go) | no | no (attach-only) |
| a dispatcher's child op | the daemon itself, over its own socket: `connect_running`, then `bridges.ensure`, waited | no (a draining daemon must not start another) | for the op |
| `api --stdio` | byte relay to `serve.sock` | yes | while it runs |
| `inbox` mutations | `connect_running`, else the same op locally | no | for the call |
| `devsandbox port` | none: forwards in its own process | no | no |
| `machine …`, a command naming a machine's instance | `connect`, then API calls and `PTY` dials over the machine's link | yes | for the lookup |
| another host's daemon | one `ssh … devsandbox fleet-link --peer <host>` per machine pair, hello as `0.0.0` (never a handoff) | yes, `links.inbound` | for the link's life |

## Handoff

A client whose `hello` is newer than the daemon's (`build` is the binary's mtime, so a rebuilt dev binary
counts) makes the old one step aside:

<Sequence title="A newer build taking over" lanes={handoffLanes} steps={handoffSteps} />

With a unit installed, the client rewrites it from its own binary and restarts it, so the managed daemon follows
upgrades. A fleet member that installed the authority's pinned build sends a forced `hello`, which hands off
whatever the versions.

## Exit

Idle, handoff and `shutdown` share one path. The listener goes first, so a successor waits for the lock instead of
seeing a live daemon. Then `closing`, the 5 s drain, the machine links, the bridges, the forwards, and the lock last.
